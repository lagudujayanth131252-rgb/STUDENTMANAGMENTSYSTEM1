2. API Architecture & Endpoint Specification

The Student Management REST API manages student academic records using an in-memory data store. Each student record conforms to the following schema:

FieldTypeConstraints
idIntegerAuto-generated, unique, immutable
grnoStringRequired, unique (General Registration Number)
nameStringRequired, min length: 2 characters
departmentStringRequired
semIntegerRequired, range: 1 to 8 (inclusive)
feesNumberRequired, must be ≥ 0
isScholarshipBooleanOptional (default: false)
emailStringRequired, unique, valid RFC email format

2.1 REST Endpoints

MethodEndpointDescriptionHTTP Status Codes
POST /api/students Register a new student record 201, 400, 409
GET /api/students Retrieve all student records (supports query filters) 200
GET /api/students/:id Retrieve single student by unique numeric ID 200, 400, 404
PUT /api/students/:id Update fields of existing student record 200, 400, 404
DELETE /api/students/:id Delete student record by numeric ID 200, 400, 404

5. Error Handling & Root Cause Analysis

5.1 HTTP Status Code Discipline

The API correctly distinguishes between all HTTP semantics:

HTTP StatusTrigger ConditionAPI Behavior
200 OKSuccessful GET, PUT, DELETE operationsReturns success object with data key
201 CreatedSuccessful POST (resource creation)Returns created record with assigned ID; distinguishes from simple 200
400 Bad RequestInvalid/malformed input, missing required fields, non-numeric IDsReturns structured error with details array for field-level errors
404 Not FoundTarget resource ID does not existAvoids empty 200 and server errors; clearly communicates absence
409 ConflictUnique constraint violation (GRNO, Email)Semantically correct — client state conflicts with server state

5.2 Standardized Error Payload Structure

Every error response maintains an explicit, uniform JSON schema enabling frontend components to map error messages directly to specific form fields:

{
  "success": false,
  "error": "<ErrorCategory>",            // e.g., "Invalid Input Values", "Resource Not Found"
  "message": "<HumanReadableSummary>",    // Descriptive sentence for the user interface
  "details": [                             // Optional array for field-level validation errors
    { "field": "<fieldName>", "error": "<specificValidationNotice>" }
  ]
}

5.3 Validation Pipeline Architecture

The POST endpoint implements a multi-layer validation pipeline in the following sequence:

LayerCheckResponse on Failure
1 — GuardEmpty body detection (Object.keys(body).length === 0)400 — "Missing Request Body"
2 — PresenceRequired field existence check (grno, name, department, sem, fees, email)400 — "Validation Failed" with details array
3 — FormatRegex email validation, integer range check for sem, non-negative check for fees400 — "Invalid Input Values" with details array
4 — UniquenessGRNO and Email uniqueness lookup against existing records409 — "Conflict" with specific field conflict message

6. Recommended Improvements

Based on test observations and industry standards, the following enhancements are recommended for production-readiness:

1

Adopt RFC 7807 — Problem Details for HTTP APIs

Standardize error responses using type, title, status, detail, and instance fields with Content-Type application/problem+json for machine-readable and interoperable error communication.

2

Schema Validation Middleware (Zod / Joi)

Replace manual field checking with declarative validation libraries such as Zod or Joi to decouple validation logic from route handlers, reducing code duplication and improving maintainability.

3

Database Persistence & Transactional Integrity

Transition from in-memory data store to a relational or document database (e.g., PostgreSQL, SQLite, MongoDB) with ACID transaction support, foreign key constraints, and persistent storage across server restarts.

4

Pagination and Sorting for GET /api/students

Implement cursor-based or offset-based pagination (page, pageSize, sortBy, sortOrder) to prevent performance degradation when the student registry grows to hundreds or thousands of records.

5

Authentication & Authorization (JWT + RBAC)

Add JSON Web Token bearer authentication with Role-Based Access Control so that only administrators can perform write operations (POST, PUT, DELETE), while read access is open or restricted to authenticated users.

6

Rate Limiting & Security Hardening

Integrate express-rate-limit to prevent brute force and DoS attacks. Add helmet for HTTP security headers and xss-clean for input sanitization to prevent XSS and injection vulnerabilities.
